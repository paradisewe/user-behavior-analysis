# Dify 整合版 Chatflow —— NL2SQL · 知识库 RAG · Agent 三合一

目标：**一条 Chatflow 演示三种能力**。用户问题先进问题分类器，按意图路由到
知识库检索（RAG）、固定 NL2SQL 取数、或 Agent 自主调工具三条支路，各自兜底、
各自回答。配好后一个公开链接即可完成全部面试演示。

前置阅读：本指南假设你已按 `nl2sql_workflow.md` 配好模型供应商与 SQL 工具，
并已用 `../dify_sync.py` 同步知识库（未同步则分支 1 检索不到内容）。

## 0. 前置条件与模型分配

| 前置 | 状态检查 |
|------|---------|
| sql_tool_service 常驻 :5057 | 浏览器开 `http://127.0.0.1:5057/health` |
| SSRF 放行已配置 | 见 `nl2sql_workflow.md` 故障排查（`SSRF_PROXY_ALLOW_PRIVATE_IPS`） |
| 模型供应商 | 现成 API（原生插件或 OpenAI-API-compatible 均可） |
| 知识库已同步且检索为混合模式 | `python ../dify_sync.py` + 数据集设置确认 |

**模型分配（每个 LLM 节点可单独选模型）**：

| 节点 | 模型档位 | 原因 |
|------|---------|------|
| 问题分类器 | 快/便宜 | 分类任务简单，省成本 |
| 分支1 查询重写 + 回答 | 快/便宜 | 语言组织类任务 |
| 分支2 SQL 生成 | **最强** | 写 SQL 对推理要求最高 |
| 分支2 结果解读 | 快/便宜 | 依样转述数据 |
| 分支3 Agent 节点 | **最强，且必须支持 tool calls** | function calling 是硬要求，选模型前确认 |

## 1. 总体架构

```
开始(question)
   │
问题分类器 ── 类别 → 支路
   ├─ 知识/方法类 ──→ 查询重写 LLM → 知识库检索 → 回答 LLM → Answer①
   ├─ 数据查询类 ──→ LLM 生成 SQL → HTTP(5057/query) → 解读 LLM → Answer②
   ├─ 组合分析类 ──→ Agent 节点(挂 query_sql 工具) ─────────→ Answer③
   └─ 其他/闲聊 ────────────────────────────────────────────→ Answer④
```

> 各支路末尾各挂一个 Answer 节点，不要汇合到同一个输出——变量引用更简单，
> 调试时一眼能看出走了哪条路。

## 2. 节点级搭建

> ⚠️ **变量引用规则（先读，省 20 分钟调试）**：本指南里所有
> `{{#start.question#}}`、`{{#llm-sql.text#}}` 等**都是简写**，表示"XX 节点的
> XX 输出变量"。实际操作时一律用**变量选择器**插入：输入框里打 `/` 或 `{`
> （或点 {x} 按钮）→ 从列表里选对应节点和变量，Dify 会生成带真实节点 ID 的
> 引用（形如 `{{#1719275352001.question#}}`）。手打简写会报
> `Variable #start.question# not found`。另外：问题分类器和知识库检索的输入
> 变量在节点顶部的**下拉框**里选，不在提示词里打；引用节点必须在被引用
> 节点的下游，否则变量列表里不会出现。

### 节点 1：开始
- 输入变量 `question`（段落文本，必填）

### 节点 2：问题分类器
- 输入变量：`{{#start.question#}}`
- 模型：快档
- 分类指令（SYSTEM 要点）：

```
你是意图分类器。根据用户问题选择唯一类别。
- 项目背景/方法论/数据口径/面试准备类问题 → 知识问答
- 问具体数字、指标、排名、对比、趋势 → 数据查询
- 要求"查数据并生成报告/解读/建议"的组合任务 → 组合分析
- 打招呼、无关闲聊、项目范围外 → 其他
判断技巧：出现"多少/排名/对比/趋势"倾向数据查询；
出现"为什么/怎么做的/是什么"倾向知识问答。
```

- 类别定义（4 个，名称即分支路由依据）：

| 类别 | 描述 |
|------|------|
| `知识问答` | 项目背景、抽样方法、指标口径、数据质量、面试问题 |
| `数据查询` | 查询具体指标数值、排名、对比、趋势 |
| `组合分析` | 查数 + 解读 + 报告类组合任务 |
| `其他` | 闲聊、超范围、无法归类 |

### 分支 1：知识问答（RAG）

**节点 3a 查询重写（LLM，快档）**：把多轮对话里的指代补全成独立检索问题。
- SYSTEM：`把用户问题改写为适合检索的独立完整问题，保留原意，只输出改写后的问题。`
- USER：`{{#start.question#}}`

**节点 3b 知识库检索**：
- 查询变量：`{{#llm-rewrite.text#}}`
- 知识库：勾选已同步的数据集（混合检索/top_k=6 已在数据集级配置，无需在此重复设置）

**节点 3c 回答（LLM，快档）→ Answer①**
- SYSTEM：

```
你是淘宝用户行为分析项目的助手，只根据检索到的上下文回答。
规则：
1. 引用结论时注明来自哪份文档
2. 上下文不足以回答时，明确说"知识库未覆盖该问题"，不要编造
3. 数字用千分位；提到数据口径时说明是抽样 5% 还是全量
```

- USER：`问题：{{#start.question#}}\n\n检索到的上下文：{{#knowledge.context#}}`
- Answer①：`{{#llm-answer1.text#}}`

### 分支 2：数据查询（NL2SQL）

与 `nl2sql_workflow.md` 的三节点完全一致，直接照搬：

**节点 4a SQL 生成（LLM，最强档）**：SYSTEM 提示词原样复制那份指南第 2 节
的"SQL 生成器"提示词（表结构 + 规则 + few-shot），USER：`{{#start.question#}}`

**节点 4b HTTP 请求**：POST `http://host.docker.internal:5057/query`，
Body：`{"sql": "{{#llm-sql.text#}}"}`

**节点 4c 解读（LLM，快档）→ Answer②**
- SYSTEM：

```
你是数据分析助手，根据 SQL 查询结果回答用户问题。
1. 结果含 error 字段时，如实说明失败原因并建议换种问法，绝不编造数据
2. 数字用千分位；注意结果行数是否被 LIMIT 截断（truncated=true 时提醒用户）
3. 提醒口径：这是全量数据（1 亿行）的结果
```

- USER：`问题：{{#start.question#}}\n\n查询结果：{{#http-request.body#}}`
- Answer②：`{{#llm-answer2.text#}}`

### 分支 3：组合分析（Agent）

**节点 5 Agent 节点**（Chatflow 节点面板里的"Agent"）：
- Agent 策略：Function Calling
- 模型：最强档，**必须支持 tool calls**
- 工具：勾选自定义工具 `query_sql`、`get_schema`（来自 openapi_sql_tool.yaml）
- 指令（SYSTEM）：

```
你是淘宝用户行为数据分析专家，拥有 SQL 查询工具。
1. 先 get_schema 确认字段口径，再 query_sql 取数；复杂问题拆成多次查询
2. 最终回答 = 数据结果 + 你的解读与建议，用 Markdown 表格呈现数据
3. 查询失败如实说明；日期范围只有 2017-11-25 ~ 12-03
4. 数字千分位；口径是全量 1 亿行
```
- 查询变量：`{{#start.question#}}`
- Answer③：`{{#agent.text#}}`

### 分支 4：兜底 → Answer④
- 直接 Answer 节点，固定话术：

```
我是淘宝用户行为分析助手，可以：
1. 回答项目方法与结论（如"抽样是怎么做的""12-02 DAU 为什么暴涨"）
2. 查全量数据（如"购买量 top5 的类目"）
3. 做组合分析（如"给我一份周末 vs 工作日的购买对比报告"）
换个问法试试？
```

## 3. 验收用例（8 条，覆盖全部分支）

| 问题 | 期望分支 | 期望结果 |
|------|---------|---------|
| 这个项目的抽样方法是什么 | 知识问答 | 命中 02_methodology，引用文档回答 |
| 面试可能会问什么 | 知识问答 | 命中 07_interview_guide |
| 12-02 的 DAU 是多少 | 数据查询 | 970,401（全量口径） |
| 购买量 top5 的类目 | 数据查询 | 5 行结果 |
| 给我一份周末和工作日购买用户数的对比报告 | 组合分析 | Agent 多次调用工具，输出表格+解读 |
| 你好 | 其他 | 兜底话术 |
| 数据质量怎么样，有缺失吗 | 知识问答 | 命中 06_data_quality |
| 帮我查一下加购用户和未加购用户的购买转化差异 | 数据查询/组合分析 | 两条支路均可，答案应含 71.58% vs 56.77% 的口径说明（用户级，抽样数据来自文档） |

第 8 条是模糊地带：分类器可能走任一数据支路，**两条支路都能给出正确答案**即算通过——这正好演示"固定管道保底、Agent 增强体验"的设计。

## 4. 已知限制与成本（诚实声明）

- **每次问答的成本**：分类器 1 次 + 支路内 2~N 次 LLM 调用。API 计费场景下
  单次问答约 3~5 次调用，演示前留意额度。
- **分类错误是主要风险点**：表现为答非所问的支路接了问题。缓解：分类指令里
  的"判断技巧"要保留；演示时如走错分支，直接换更明确措辞的问法即可。
- **Agent 分支是亮点不是保底**：固定 NL2SQL 分支失败率低于 Agent 分支；
  演示顺序建议先 NL2SQL 再 Agent。
- **数据出网**：SQL 结果（聚合数字、脱敏类目 ID）会发送到云端 API；
  数据集本身是脱敏公开数据，无隐私风险，但这是可以主动讲的架构决策
  （查数在本地、理解出云端）。
- **想再稳一点**：删掉分支 3，只保留知识问答 + NL2SQL 两分支，
  分类器退化为二分类，出错率进一步下降。
