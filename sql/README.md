# SQL 分析方案

与 `python/` 平级的 SQL 分析项目，用 **DuckDB** 作为执行引擎。

## 为什么要有 SQL 方案

- **职业必备**：数据分析师日常 80% 的时间在写 SQL
- **场景互补**：SQL 适合全量数据、批量统计；Python 适合可视化和建模
- **交叉验证**：同一份数据用两种工具跑，结果一致说明分析可信

## 为什么用 DuckDB

- 零安装、零导入，一行命令直接读 Parquet
- 支持完整 SQL 语法（窗口函数、CTE、FILTER 等）
- 单文件嵌入式，速度接近 ClickHouse
- 和 pandas 无缝互操作

## SQL vs Python 交叉验证

用**全量 1 亿行**的 SQL 结果，与 **Python 分层等比例抽样（5%，约 500 万行、4.9 万用户）** 的结果对比：

### 核心指标对比

| 指标 | Python（抽样 5%） | SQL（全量 1 亿行） | 差异 |
|------|------------------|------------------|------|
| **行为分布** | | | |
| pv 占比 | 89.56% | 89.58% | -0.02% |
| cart 占比 | 5.49% | 5.52% | -0.03% |
| fav 占比 | 2.93% | 2.88% | +0.05% |
| buy 占比 | 2.02% | 2.01% | +0.01% |
| **用户级漏斗转化率** | | | |
| 浏览 → 收藏 | 39.79% | 39.61% | +0.18% |
| 浏览 → 加购 | 74.21% | 75.09% | -0.88% |
| 浏览 → 购买 | 67.82% | 68.33% | -0.51% |
| **用户-商品级漏斗** | | | |
| pv→cart 转化率 | 1.07% | 1.07% | **0.00%** |
| pv→buy 转化率 | 1.41% | 1.40% | +0.01% |
| cart→buy 转化率 | 5.98% | 6.06% | -0.08% |
| **复购分析** | | | |
| 复购率 | 65.81% | 66.01% | -0.20% |
| **用户分层** | | | |
| 已购买 | 67.8% | 68.06% | -0.26% |
| 加购未购买 | 21.1% | 21.04% | +0.06% |
| 仅浏览 | 6.2% | 6.03% | +0.17% |
| 仅收藏 | 5.2% | 4.87% | +0.33% |

### 结论

**所有核心指标的差异均 < 1%**，行为分布、pv→cart 转化率等关键指标的差异甚至 < 0.1%。

**验证了用户级分层等比例抽样方法的正确性——用 5% 的数据量（500 万行 / 1 亿行），可以还原出接近全量的分析结论。**

### 用户分层维度的说明

用户分层维度的差异略大于行为级指标，原因是：

1. 分层仅按「活跃度」分层，未对「是否购买」这一维度做二次分层
2. **用户级指标的方差天然大于行为级指标**

**改进方向**：加入「用户购买行为」作为第二分层维度，进一步降低偏差。

## SQL 结果中的三个额外发现

### 1. 数据窗口验证

`04_daily_trend.csv` 显示：

```
2017-11-01 ~ 11-24：日活仅几十 ~ 几百（边界数据）
2017-11-25 ~ 12-03：日活 70 万 ~ 97 万（核心窗口）
2017-12-04 ~ 12-31：日活 1 ~ 158（边界数据）
```

这印证了天池数据的真实窗口就是 **2017-11-25 ~ 2017-12-03**，其他天的数据是稀疏的边缘记录。Python 的清洗逻辑（`filter_time_range`）过滤到该窗口是正确的。

### 2. 用户活跃的时间峰值

`05_hourly_activity.csv` 显示：

- **低谷**：凌晨 3~4 点（pv 约 45~52 万）
- **次高峰**：凌晨 0 点（pv 306 万）
- **主高峰**：晚上 21~22 点（pv 745~754 万）

淘宝用户的活跃高峰是晚上 9~10 点，与白天分散活跃的规律显著不同。

### 3. 类目 TOP10 基本稳定

Python 抽样和 SQL 全量的 TOP10 类目**名单基本一致**（顺序略有差异），说明抽样对类目排行的估计是可靠的。

## 技术细节

### 时间戳处理

DuckDB 里把 Unix 秒级时间戳转日期：

```sql
DATE_TRUNC('day', TO_TIMESTAMP(timestamp))::DATE
```

比 SQL Server 的 `DATEADD(SECOND, timestamp, '1970-01-01')` 简洁得多。

### 为什么 DuckDB 比 MySQL 更适合这个项目

| 维度 | MySQL 8.0 | DuckDB |
|------|----------|--------|
| 定位 | OLTP（高并发事务） | OLAP（分析查询） |
| 存储 | 行式存储 | 列式存储 |
| 执行 | 火山模型（逐行） | 向量化（批量） |
| 导入 | 需手动导入 3.42 GB | 直接读 Parquet |
| 部署 | 客户端-服务器 | 嵌入式单文件 |

DuckDB 的列式存储 + 向量化执行，让它在聚合、扫描等分析操作上比 MySQL 快 5~100 倍。

### 全量 SQL 的性能

- **数据规模**：1 亿行、3.42 GB Parquet
- **查询耗时**：单个查询 3~10 秒
- **全流程耗时**：8 个查询约 1~3 分钟

DuckDB 直接读 Parquet，无需导入数据库，显著降低使用门槛。
